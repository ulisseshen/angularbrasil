# Acessibilidade no Angular

A web é usada por uma grande variedade de pessoas, incluindo aquelas com deficiências visuais ou motoras.
Existe uma variedade de tecnologias assistivas que tornam muito mais fácil para esses grupos interagir com aplicações de software baseadas na web.
Além disso, projetar uma aplicação para ser mais acessível geralmente melhora a experiência do usuário para todos.

Para uma introdução aprofundada às questões e técnicas de design de aplicações acessíveis, veja o curso [Learn Accessibility](https://web.dev/learn/accessibility/) do web.dev, do Google.

Esta página discute as boas práticas para projetar aplicações Angular que funcionem bem para todos os usuários, incluindo aqueles que dependem de tecnologias assistivas.

## Atributos de acessibilidade {#accessibility-attributes}

Construir experiências web acessíveis frequentemente envolve definir [atributos Accessible Rich Internet Applications \(ARIA\)](https://web.dev/learn/accessibility/aria-html/) para fornecer significado semântico onde ele poderia estar faltando.
Use a sintaxe de template de [binding de atributo](guide/templates/binding#binding-dynamic-properties-and-attributes) para controlar os valores dos atributos relacionados à acessibilidade.

### Atributos e propriedades ARIA {#aria-attributes-and-properties}

Ao fazer binding com atributos ARIA no Angular, você pode usá-los diretamente, como qualquer outro atributo HTML.

```html
<button [aria-label]="myActionLabel">…</button>
```

Atributos ARIA estáticos funcionam como atributos HTML comuns.

```html
<button aria-label="Save document">…</button>
```

HELPFUL: Por convenção, atributos HTML usam nomes em minúsculas \(`tabindex`\), enquanto propriedades usam nomes em camelCase \(`tabIndex`\).

Alguns padrões ARIA expõem APIs do DOM ou inputs de diretivas que aceitam valores estruturados (por exemplo, coleções de referências a `Element`). Use bindings de propriedade padrão nesses casos, para que a relação subjacente permaneça sincronizada.

```angular-ts
@Component({
  template: `
    <h2 #dialogTitle>Attention</h2>
    <p #dialogDescription>Please review your answers before continuing.</p>

    <section role="dialog" [ariaLabelledByElements]="[dialogTitle, dialogDescription]">
      <ng-content />
    </section>
  `,
})
export class ReviewDialog {}
```

Aqui, `[ariaLabelledByElements]` aceita um array de elementos, então o binding de propriedade mantém as referências dos elementos atualizadas sempre que os dados do template mudam.

Veja o [guia de binding](guide/templates/binding#aria-attributes) para um resumo da sintaxe de atributos ARIA.

## Components de UI do Angular {#angular-ui-components}

A biblioteca [Angular Material](https://material.angular.dev), mantida pela equipe do Angular, é um conjunto de components de UI reutilizáveis que tem como objetivo ser totalmente acessível.
O [Component Development Kit (CDK)](https://material.angular.dev/cdk/categories) inclui o pacote `a11y`, que fornece ferramentas para apoiar várias áreas da acessibilidade.
Por exemplo:

- `LiveAnnouncer` é usado para anunciar mensagens para usuários de leitores de tela usando uma região `aria-live`.
  Veja a documentação do W3C para mais informações sobre [regiões aria-live](https://www.w3.org/WAI/PF/aria-1.1/states_and_properties#aria-live).

- A diretiva `cdkTrapFocus` mantém o foco da tecla Tab dentro de um elemento.
  Use-a para criar experiências acessíveis para components como caixas de diálogo modais, nas quais o foco deve ser restrito.

Para detalhes completos dessas e de outras ferramentas, veja a [visão geral de acessibilidade do Angular CDK](https://material.angular.dev/cdk/a11y/overview).

Para components com estilo personalizado que precisam de padrões de interação WAI-ARIA reutilizáveis, o [Angular Aria](guide/aria/overview) fornece diretivas headless para padrões como accordion, combobox, listbox, menu, tabs e toolbar.
Essas diretivas cuidam da interação por teclado, dos atributos ARIA, do gerenciamento de foco e do suporte a leitores de tela, enquanto você fornece a estrutura HTML e o estilo da sua aplicação.

### Aumentando elementos nativos {#augmenting-native-elements}

Elementos HTML nativos já incorporam vários padrões de interação padrão que são importantes para a acessibilidade.
Ao criar components Angular, você deve reutilizar esses elementos nativos diretamente sempre que possível, em vez de reimplementar comportamentos já bem suportados.

Por exemplo, em vez de criar um elemento personalizado para uma nova variação de botão, crie um component que use um seletor de atributo com um elemento `<button>` nativo.
Isso se aplica com mais frequência a `<button>` e `<a>`, mas pode ser usado com muitos outros tipos de elemento.

Você pode ver exemplos desse padrão no Angular Material:
[`MatButton`](https://github.com/angular/components/blob/main/src/material/button/button.ts#L33C3-L36C5), [`MatTabNav`](https://github.com/angular/components/blob/main/src/material/tabs/tab-nav-bar/tab-nav-bar.ts#L62) e [`MatTable`](https://github.com/angular/components/blob/main/src/material/table/table.ts#L40).

### Usando containers para elementos nativos {#using-containers-for-native-elements}

Às vezes, usar o elemento nativo apropriado exige um elemento container.
Por exemplo, o elemento nativo `<input>` não pode ter filhos, então quaisquer components personalizados de entrada de texto precisam envolver um `<input>` com elementos extras.
Ao simplesmente incluir `<input>` no template do seu component personalizado, é impossível para os usuários do seu component definir propriedades e atributos arbitrários no elemento `<input>`.
Em vez disso, crie um component container que use projeção de conteúdo para incluir o controle nativo na API do component.

Você pode ver o [`MatFormField`](https://material.angular.dev/components/form-field/overview) como exemplo desse padrão.

## Roteamento {#routing}

### Gerenciamento de foco após a navegação {#focus-management-after-navigation}

Rastrear e controlar o [foco](https://web.dev/learn/accessibility/focus/) em uma UI é uma consideração importante ao projetar para acessibilidade.
Ao usar o roteamento do Angular, você deve decidir para onde o foco da página vai após a navegação.

Para evitar depender somente de pistas visuais, você precisa garantir que o seu código de roteamento atualize o foco após a navegação da página.
Use o evento `NavigationEnd` do service `Router` para saber quando atualizar o foco.

O exemplo a seguir mostra como encontrar e focar o cabeçalho do conteúdo principal no DOM após a navegação.

```ts
router.events.pipe(filter((e) => e instanceof NavigationEnd)).subscribe(() => {
  const mainHeader = document.querySelector('#main-content-header');
  if (mainHeader) {
    mainHeader.focus();
  }
});
```

Em uma aplicação real, o elemento que recebe o foco depende da estrutura e do layout específicos da sua aplicação.
O elemento focado deve colocar os usuários em posição de passar imediatamente para o conteúdo principal que acabou de ser exibido pela rota.
Você deve evitar situações em que o foco volte para o elemento `body` após uma mudança de rota.

### Identificação de links ativos {#active-links-identification}

Classes CSS aplicadas a elementos `RouterLink` ativos, como as do `RouterLinkActive`, fornecem uma pista visual para identificar o link ativo.
Infelizmente, uma pista visual não ajuda usuários cegos ou com deficiência visual.
Aplicar o atributo `aria-current` ao elemento pode ajudar a identificar o link ativo.
Para mais informações, veja [Mozilla Developer Network \(MDN\) aria-current](https://developer.mozilla.org/docs/Web/Accessibility/ARIA/Attributes/aria-current)).

A diretiva `RouterLinkActive` fornece o input `ariaCurrentWhenActive`, que define o `aria-current` com um valor especificado quando o link se torna ativo.

O exemplo a seguir mostra como aplicar a classe `active-page` aos links ativos, além de definir o atributo `aria-current` como `"page"` quando eles estão ativos:

```angular-html
<nav>
  <a routerLink="home" routerLinkActive="active-page" ariaCurrentWhenActive="page"> Home </a>
  <a routerLink="about" routerLinkActive="active-page" ariaCurrentWhenActive="page"> About </a>
  <a routerLink="shop" routerLinkActive="active-page" ariaCurrentWhenActive="page"> Shop </a>
</nav>
```

## Carregamento adiado (deferred) {#deferred-loading}

Ao usar blocos `@defer` do Angular para carregamento preguiçoso (lazy) de conteúdo, considere as implicações de acessibilidade para usuários que usam tecnologias assistivas.
Leitores de tela podem não anunciar automaticamente mudanças de conteúdo quando components deferidos são carregados, o que pode deixar os usuários sem saber do novo conteúdo.

Para garantir que as mudanças de conteúdo deferido sejam anunciadas corretamente, envolva os seus blocos `@defer` em elementos com regiões ARIA live apropriadas.
Para orientações detalhadas e exemplos, veja a [seção de acessibilidade no guia de defer](/guide/templates/defer#keep-accessibility-in-mind).

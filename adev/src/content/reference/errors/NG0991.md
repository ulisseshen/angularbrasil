# Resource concluído antes de produzir um valor {#resource-completed-before-producing-a-value}

Este erro acontece quando um resource baseado em `Observable` — [`rxResource`](/ecosystem/rxjs-interop#using-rxresource-for-async-data) ou [`httpResource`](/api/common/http/httpResource) — termina (completa) sem nunca enviar um valor ou um erro.

Um resource sempre precisa terminar com _algo_: um valor que ele carregou ou um erro explicando o que deu errado. Um Observable que simplesmente completa em silêncio não fornece nenhuma dessas coisas ao Angular, então o Angular não sabe o que colocar no resource, e lança este erro.

## Com `httpResource` {#with-httpresource}

O `httpResource` não oferece um Observable para você escrever — ele faz a chamada HTTP internamente, por meio do `HttpClient`, e completa quando a resposta chega. Então, se você está vendo este erro vindo do `httpResource`, o problema não é a requisição em si; algo que fica antes dela está engolindo a resposta antes que ela chegue.

O suspeito mais comum é um `HttpInterceptor` que captura um erro e não reemite nada, o mesmo erro de usar `EMPTY` mencionado abaixo, mas agora dentro de um interceptor em vez do seu próprio código:

```typescript
@Injectable()
class MyInterceptor implements HttpInterceptor {
  intercept(req: HttpRequest<unknown>, next: HttpHandler) {
    return next.handle(req).pipe(
      // RUIM: mesmo problema de `catchError(() => EMPTY)` em um `stream` —
      // a requisição completa sem resposta e sem erro, e qualquer httpResource
      // que dependa dela recebe o NG0991.
      catchError(() => EMPTY),
    );
  }
}
```

Corrija da mesma forma que faria em um pipeline de interceptors em geral: deixe o erro se propagar (remova o `catchError`) ou substitua-o por algo que realmente resolva a requisição, como `of(new HttpResponse({body: fallbackValue}))`.

## Com `rxResource` {#with-rxresource}

A forma mais comum de causar isso acidentalmente é capturar um erro e engoli-lo com `EMPTY`:

```typescript
import {rxResource} from '@angular/core/rxjs-interop';
import {EMPTY, catchError} from 'rxjs';

const userResource = rxResource({
  params: () => ({id: userId()}),
  stream: ({params}) =>
    this.http.get(`/users/${params.id}`).pipe(
      // RUIM: isso esconde o erro completamente. O Observable simplesmente
      // completa sem nada, e o resource não tem valor nem erro para mostrar —
      // é isso que dispara o NG0991.
      catchError(() => EMPTY),
    ),
});
```

Outra forma comum de isso acontecer é combinar vários Observables (com `merge`, `race` e similares) em que um deles pode completar sozinho antes de emitir qualquer coisa, sem um `startWith(...)` que garanta um valor inicial. Se nenhuma das fontes combinadas emitir nada antes de todas completarem, o stream combinado também completa vazio.

Escolha a correção que faça sentido para o seu caso:

**Deixe o erro passar.** Se você não precisa tratar o erro por conta própria, basta remover o `catchError`. O resource vai para o estado `error`, que você já pode verificar com `userResource.error()`.

```typescript
stream: ({params}) => this.http.get(`/users/${params.id}`),
```

**Recupere com um valor de fallback.** Se você prefere mostrar algo em vez de um erro, use `catchError` para retornar um Observable que emita um valor, como `of(...)`:

```typescript
import {of, catchError} from 'rxjs';

stream: ({params}) =>
  this.http.get(`/users/${params.id}`).pipe(
    catchError(() => of(null)), // o resource resolve com `null` em vez de dar erro
  ),
```

De qualquer forma, garanta que o Observable retornado por `stream` sempre emita pelo menos um valor ou um erro antes de completar.

## Onde você realmente verá este erro {#where-youll-actually-see-this-error}

O erro não é lançado quando o resource é criado, e nem necessariamente onde a requisição completa. Ele é lançado na próxima vez que algo ler o valor do resource, por exemplo `userResource.value()` em um binding de template. Isso pode fazer parecer que o bug está em outro lugar da aplicação, quando a causa real está antes (o `stream` completando vazio, ou um interceptor engolindo a resposta).

Se nada no seu código verifica o status do resource antes de ler `.value()`, este erro pode subir até o `ErrorHandler` global do Angular, como qualquer outro erro não tratado lançado durante a renderização de um template.

Há duas formas de reduzir o impacto disso, da mais para a menos recomendada:

1. **Corrija na raiz**, usando uma das abordagens acima, para que o resource nunca chegue a esse estado.
2. **Proteja as leituras de `.value()`** como defesa em profundidade, caso algo que você não controla totalmente (um interceptor ou serviço de terceiros, por exemplo) complete vazio de forma inesperada. Verifique `.hasValue()` ou `.status()` antes de ler `.value()`, por exemplo com `@if (userResource.hasValue()) { {{ userResource.value() }} }`, em vez de ler `.value()` incondicionalmente.

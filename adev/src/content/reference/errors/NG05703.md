# Mudança suspeita na origem de URL

Este erro ocorre em ambientes de Server-Side Rendering (SSR) quando a resolução de uma URL resulta em uma mudança inesperada de origem. Essa verificação é um recurso de segurança do `@angular/platform-server`, projetado para proteger sua aplicação contra Server-Side Request Forgery (SSRF) e outros contornos de segurança.

## Descrição {#description}

Para realizar requisições HTTP e processar os estados de rota durante o SSR, o Angular precisa resolver URLs relativas em URLs absolutas.

Durante esse processo de resolução, o Angular valida que a URL resolvida não aponta inesperadamente para uma origem externa ou não confiável. Se uma URL se comporta como um caminho relativo, mas é resolvida para uma origem diferente, o Angular lança `NG05703` e bloqueia a requisição ou a navegação.

### Causas comuns {#common-causes}

- **Tentativas de sequestro com barra invertida (open redirects / bypass de SSRF):** Caminhos relativos que começam com barras e barras invertidas (como `/\\attacker.com/path` ou `\\\\attacker.com/path`) podem ser interpretados de forma diferente por browsers e por parsers de URL do lado do servidor. Em algumas implementações de parser, eles são resolvidos para uma URL absoluta apontando para `attacker.com`. O Angular detecta essa divergência e bloqueia a resolução.
- **Mudanças de estado não permitidas para origens diferentes:** Navegações ou atualizações de URL (por exemplo, usando `location.replaceState` ou `location.pushState`) que alteram a origem da aplicação, quando o ambiente está configurado para restringir mudanças de URL apenas à origem atual.
- **Divergência da URL de bootstrap do SSR:** Na renderização no servidor, se a `url` passada ao renderer não estiver alinhada com a origem base configurada para a aplicação (como `APP_BASE_HREF`), o router pode tentar sincronizar a localização na inicialização, causando uma mudança de origem não permitida.
- **Esquemas de protocolo ofuscados:** URLs absolutas com protocolos ofuscados ou malformados (por exemplo, `ht\ntp://evil.com/path`) que tentam contornar as verificações de origem.

## Depurando o erro {#debugging-the-error}

Verifique a URL que disparou o erro. Garanta que ela não contenha barras invertidas inesperadas, quebras de linha ou outros caracteres que possam causar anomalias de parsing:

- Evite usar barras invertidas (`\`) em URLs relativas ou caminhos de rotas.
- Certifique-se de que quaisquer URLs ou parâmetros de query fornecidos pelo usuário sejam validados e sanitizados antes de serem processados no SSR.
- **Alinhe a URL de bootstrap do SSR com a URL base configurada:** Se o erro ocorrer na inicialização em um ambiente SSR, garanta que a `url` passada ao renderer corresponda à origem/host base esperado (por exemplo, `APP_BASE_HREF`). Evite usar URLs dinâmicas vindas de cabeçalhos brutos da requisição (como `X-Forwarded-Host`) se elas não corresponderem à origem confiável da aplicação.
- Se você quiser intencionalmente fazer requisições para outro domínio por meio de uma URL relativa ao protocolo (`//other-domain.com/path`), garanta que isso esteja permitido na configuração ou use um esquema explícito (`http://` ou `https://`).
